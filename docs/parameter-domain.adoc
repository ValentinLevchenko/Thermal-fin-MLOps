= Parameter domain and fixed settings

This document defines the parameters varied in the campaign, their bounds,
and the settings that stayed fixed. All quantities are nondimensional.

== Varied parameters

* L (fin length): from 0.5 to 2.5
* t (fin thickness): from 0.2 to 0.5
* Bi (Biot number): from 0.01 to 1, log scale


== Fixed settings

* Generator: feelpp/feelpp, commit 44487393868854b53e47e82217d3a0fbc557c8d1
* 3D case, 4 fins, fin spacing d=0.75, box shapes 
* Materials: generator defaults, never changed
* Heat flux: 1 (nondimensional)
* Air temperature: 0
* Mesh size: h_max = 0.1

== Why these bounds

* All corners are valid: the 9 combinations of L = 0.5, 1, 2.5 and t = 0.2, 0.25, 0.5 have all zones, the correct heated face,
the correct volume and min_gamma between 0.12 and 0.30 (`docs/evidence/domain-corners.csv`).
* t from 0.2: with h_max = 0.1, t = 0.1 and t = 0.15 give degenerate elements (min_gamma between 0 and 0.013), 
while t = 0.2 gives min_gamma >= 0.12 (`docs/evidence/t-lower-bound.csv`). The fin must hold at least two elements
through its thickness (t >= 2h_max). Thinner fins would need a smaller h, which makes the meshes much bigger and the campaign more expensive.
* t up to 0.5: stays thinner than the fin spacing d = 0.75.
* L from 0.5: the mesh is not the limit (L = 0.1 and 0.25 pass, `docs/evidence/L-lower-bound.csv`). 
The reason is physical: L is the overhang of the fin beyond the post. Below 0.5 the plate barely extends past the post,
so it no longer acts as a real fin. At L = 0.5 the plate area is already 4 times the post cross-section.
* L up to 2.5: the generator default, and the most expensive case (about 368 000 elements at t = 0.5).
* Bi from 0.01 to 1: the bounds written by the generator in the case JSON. Bi cannot go to 0: without cooling, 
the heat entering at the root has nowhere to go and there is no steady solution.

== Mesh quality threshold

A case is accepted if its worst element has gamma >= 0.1. Gamma is 1 for a perfect tetrahedron and 0 for a flat one.
All rejected cases are below 0.013 and all accepted cases are above 0.12, so the decision does not depend on the exact threshold value.

== Running the check

The script expects the Feel++ repository cloned next to this repository, on commit 44487393868854b53e47e82217d3a0fbc557c8d1:

`../feelpp/toolboxes/generator/cases/thermal_fin/case_generator_thermal_fin.py`

Another location can be given with '--generator <path>' or the environment variable 'FEELPP_THERMAL_FIN_GENERATOR'.
The script stops if the checkout is not on the pinned commit.


== Sampling

* Method: Latin Hypercube Sampling. Each parameter range is split into n slices and each slice receives
exactly one sample, so every part of each range is covered even with few simulations. Pure random sampling 
can leave parts of the domain empty and a grid needs too many simulations in 3D (10 values per parameter = 1000 runs).
* Bi is sampled on a log scale (log10 between -2 and 0) because it spans two decades, so there are as many 
samples between 0.01 and 0.1 as between 0.1 and 1.
* Seed: 2026, stored in `config/campaign.json`. The same seed always gives the same samples. The seed is fixed 
before any simulation and is not changed afterwards.
* Command: `uv run python -m thermal_surrogate.sampling --n <number of samples>` 
writes `data/samples.csv`.
* Each sample has a stable ID (s0000, s0001, ...), used later for the train-validation-test split.
* Tests in `tests/test_sampling.py` check reproducibility, bounds, unique IDs and that Bi covers both decades.
* The number of samples is chosen in the sample budget sub-issue.



== Sample budget

Three corner cases were meshed (h_max = 0.1) and solved on Gaya with
`slurm/budget.sh` (job 93127, partition public, 1 MPI rank,
image /data/cemosis/benchmark/feelpp-noble.sif, Apptainer 1.4.3, Gmsh 4.12.1).
Results are in `docs/evidence/budget-timings.csv`.

* Cheapest case (L = 0.5, t = 0.2): 35 451 elements, 12 s in total.
* Most expensive case (L = 2.5, t = 0.5): 367 603 elements, 32 s in total.
* Times include meshing and container start-up (about 3 to 4 s per run).

Taking the worst case (32 s per sample), 200 samples cost at most about 1.8 core-hours.

* Smoke campaign: 5 samples, to test the full pipeline end to end. (`--n 5 --output data/samples-smoke.csv`)
* Full campaign: 200 samples (140 train, 30 validation, 30 test with a 70/15/15 split). (`--n 200 --output data/samples.csv`)
* The budget must be approved by the teaching team before the full campaign.

* Peak memory of the largest case, measured with `/usr/bin/time -v` (job 93131_2):
1.9 GB, well below the 8 GB requested.
* Repeatability: the largest case was run twice (jobs 93127_2 and 93131_2) and gave 
the same mean root temperature to all printed digits (1.4817411834492460).

Raw outputs (meshes, fields, logs) are kept on Gaya in
`~/M2/budget-results/` and `~/M2/logs/` (job 93127); they can be regenerated with `slurm/budget.sh`.
